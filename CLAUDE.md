# CLAUDE.md

Instructions for Claude Code working in this repo. Read `SPEC.md` first; it is the plan of record. The current phase is the first unchecked box in SPEC §7.

## What this is
Stockroom: an ops agent over a fictional distributor's messy ERP data. It uses real M5 sales, synthetic ERP attributes and injected data-quality issues. The portfolio value is the **eval table** and the **FDE engagement artefacts**, not the UI.

## Commands
```bash
uv sync                                        # install (or: pip install -e ".[dev]")
uv run python scripts/fetch_m5.py              # download M5 (~325 MB) into data/m5/
uv run python -m stockroom.data.pipeline       # truth -> raw+dirt -> core   (~20s)
uv run python -m stockroom.data.pipeline --core  # re-run cleaning only
uv run python -m stockroom.forecast.train       # backtest + final model + 28-day forecasts (~15 min, 2 cores)
uv run python -m stockroom.approvals list       # PO drafts; approve/reject is human-only
uv run python -m stockroom.agent --steps        # chat with the agent (needs ANTHROPIC_API_KEY)
uv run python -m evals.p4_live_session          # 5-question live check, writes docs/results (~$0.10)
uv run stockroom-mcp                           # MCP server over stdio (Claude Code launches it via .mcp.json)
uv run stockroom-mcp --http                    # same, streamable HTTP on 127.0.0.1:8765/mcp (loopback only)
uv run python -m evals.p6_claude_code_session  # 8 eval questions through `claude -p` + MCP only (~$0.40)
(cd web && npm ci && npm run build)            # Next.js static export -> web/out (served by the API)
uv run stockroom-web                           # API + UI on http://127.0.0.1:7860 (demo guards: see api/app.py Settings)
docker build -t stockroom-demo .               # the public demo image (never contains ground_truth.duckdb)
uv run python scripts/screenshot_demo.py       # headless screenshots of a running demo (~$0.05 of API)
HF_TOKEN=... uv run python scripts/deploy_space.py [--dry-run]   # publish to the HF Space
uv run pytest -q                               # tests (need data built)
uv run python -m evals.build_questions         # rebuild evals/questions.jsonl from ground truth (deterministic)
uv run python -m evals.run --config sonnet_v2 --budget 5   # full eval, resumable (~$2.50); configs in evals/run.py
uv run python -m evals.rescore <run-id>        # re-score stored answers after a scorer change (no API calls)
uv run python -m evals.report                  # regenerate docs/results/eval.md + chart from runs/evals/
uv run python -m evals.smoke check <run-id>    # compare a 20-question smoke run with evals/baseline.json (CI does this)
```
`make data`, `make forecast`, `make test`, `make lint` wrap these on macOS/Linux. Install the secret guard once per clone: `ln -sf ../../scripts/pre-commit .git/hooks/pre-commit`. The API key lives in an untracked env file, never in the repo.

## Hard rules
1. **Tools never touch `ground_truth.duckdb`.** Only `tests/` and `evals/` may attach it. If you are writing code under `src/stockroom/tools` or `src/stockroom/agent` and you type `TRUTH_DB`, stop.
2. **The cleaning layer (`sql/core.sql`) must detect issues from `raw.*` alone.** Never read `dirt_manifest.json` outside tests and evals.
3. **Agent-facing SQL is read-only and `core.*`-only.** Every change to the SQL guard needs a test proving a new bypass is blocked.
4. **No tool can approve or send a PO.** Drafts only (`po_drafts` in `app.duckdb`, status `PENDING_APPROVAL`). Decisions go through `stockroom.approvals`, which must never be registered as a tool. Open `app.duckdb` only through `appdb.app_session()`, never hold a connection: long-lived processes (MCP server, API) would lock out approvals. In the web API, deciding a draft is a human HTTP route, never something the agent can reach.
5. **Numbers in docs come from runs, not estimates.** Results tables in `docs/results/` are generated by scripts, with the command that produced them written above the table.
6. The `raw` schema mode of `stockroom.tools.call(..., schema="raw")` exists only for the eval ablation. The model can never select it, and no product code may use it.
7. Adapters call tools only through `stockroom.tools.call(name, args)`. Every tool returns `{"data", "caveats", "provenance"}`. Data-quality caveats must reach the model; that is how it avoids answering "0" for a missing day.
8. Record any decision that would be expensive to reverse as an ADR in `docs/adr/` (`/adr <title>`).

## Conventions
- Python 3.11+, type hints everywhere, `ruff` for lint/format, `pytest`.
- SQL in `.sql` files when it is more than ~10 lines.
- Model IDs come from env (`STOCKROOM_MODEL`, `STOCKROOM_CHEAP_MODEL`); defaults are in `config.py`.
- Small commits, one concern each, message in imperative mood.
- When a phase finishes: tick it in SPEC §7, add its "done" evidence, commit.
